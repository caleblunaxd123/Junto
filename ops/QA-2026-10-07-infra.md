# JUNTO — correo, seguridad y preparación de infraestructura

Base: `main`/`origin/main` en `d06e697`; el fetch final no encontró commits adicionales. Se preservaron las bases y archivos privados. No se publicó ni se modificó infraestructura de producción.

## Cambios

- Verificación, recuperación y bienvenida usan la identidad clara de JUNTO, HTML de tablas y estilos inline, texto alternativo y contenido escapado. El código de verificación ya no aparece en el asunto. La bienvenida no inventa un enlace si falta una URL HTTPS.
- `email:check` comprueba TLS/autenticación sin enviar mensajes ni imprimir contraseñas. Errores de pruebas de correo y Sentry usan tipo/código/estado, sin mensajes privados del proveedor.
- Notificaciones: se comprueba el ticket de Expo aunque HTTP sea 200; las aceptadas guardan solo metadatos para comprobar el recibo tras 15 minutos. Comprobación cada cinco minutos con reserva entre instancias, limpieza a las 24 horas, límite de seis solicitudes concurrentes, timeout y ninguna repetición ciega del envío. Un token inválido antiguo no elimina el nuevo. La eliminación de cuenta borra estos metadatos y no se recrean al competir con una respuesta de Expo.
- Nueva migración aditiva `20261007220000_push_receipts`. Siete migraciones en total.
- Configuración de distribución rechaza URLs privadas/locales/reservadas, alias IPv4 y IPv6 no globales. No equivale a verificar la resolución DNS ni la disponibilidad del servidor.
- Actualizaciones compatibles de dependencias y Sentry 10; se retiró Firebase Admin sin uso. Expo SDK y React Native no se migraron de versión mayor.

- 58 pruebas de dominio API y 66 pruebas ops: **124, sin fallos**.
- API compila; typecheck y lint móvil pasan. `git diff --check` pasa.
- Diez integraciones pasan: eliminación, Google, idempotencia de gastos, correo compartido, comprobantes/comentarios, cuentas rápidas, hardening, seguridad/UX, rediseño y notificaciones.
- Base aislada **nueva** `junto_smtp_push_qa_20261007`: siete migraciones aplicadas desde cero, diferencia con Prisma vacía. La primera pasada sobre una base de QA ya usada rechazó correctamente la imagen fija como duplicada; no se borraron datos para ocultar ese resultado. Se repitió el recorrido en esta base nueva.
- El receptor SMTP de integración es local y Expo está simulado en las pruebas push: no acredita entrega externa. Verificación SMTP real, sin enviar mensaje: `EAUTH`, `535`.
- Lockfile comprobado con `npm ci --dry-run --ignore-scripts`. Primera instalación Linux con Node 22 y compilación correctas, pero las pruebas en `bookworm-slim` fallaron con OpenSSL ausente. Se repitió instalando OpenSSL antes de generar Prisma: instalación limpia, compilación y **58 pruebas pasan**. No se copiaron archivos `.env` al entorno de compilación.
- Auditoría completa: **52 avisos** (1 bajo, 21 moderados, 30 altos), sin críticos; aún no es una aprobación para publicar. `npm audit --omit=dev --workspace=apps/api` informa dos altos (`braces`, `chokidar`) en el árbol compartido del monorepo. Hay que revisar alcance y probar las actualizaciones restantes, no usar `--force` para cambiar Expo sin validación nativa.

## Bloqueos reales

La contraseña SSH no resuelve el acceso: el VPS solo admite claves y rechaza la disponible. El propietario debe proporcionar una ruta de clave ya autorizada o autorizar la pública desde la consola. Gmail exige una credencial SMTP válida de esa misma cuenta. Los detalles y la secuencia de despliegue están en `ops/CONTABO-CORREO.md`.

No se cambiaron DNS ni TLS de Cloudflare, no se aplicaron migraciones al VPS, no se recibieron correos reales en Gmail/Outlook y no se envió WhatsApp. EAS/FCM, cliente real de correo, boletas reales, TalkBack y teléfonos siguen pendientes según `RELEASE_CHECKLIST.md`.
